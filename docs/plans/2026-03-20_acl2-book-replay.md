# Plan: ACL2 Book Replay in Lean

**Date:** 2026-03-20
**Repo:** github.com/septract/ACL2Lean (fork of alok/ACL2Lean)
**Goal:** Import any ACL2 book and replay its proofs in Lean, using ACL2 as
an untrusted proof-search oracle with Lean's kernel as the sole trust anchor.

### What's missing for book replay

1. **ACL2 books corpus** — No access to `books/sorting/` in this repo.
   The legacy prototype has a full ACL2 fork as a submodule.
2. **Sorting-specific primitives** — `orderedp`, `insert`, `isort`, `perm`,
   `how-many` need to be defined over SExpr or auto-generated by the translator.
3. **Translator maturity** — Current translator handles basic defun/defthm but
   needs to: generate termination obligations, handle `include-book` chains,
   emit `decreasing_by` clauses, translate the sorting corpus end-to-end.
4. **Hint bridge (not yet built)** — Need to build the bridge that runs ACL2,
   captures proof transcripts, and parses them into the structured types
   already defined in `Syntax.lean` (`ProofInstruction`, `GoalHint`, etc.).
5. **Proof replay tactic (not yet built)** — Need `acl2_replay` that takes
   parsed hints and drives Lean tactics. Currently only `acl2_simp`/`acl2_grind`
   exist as manual-use tactics.
6. **ACL2 instrumentation** — Need ACL2 running to produce transcripts.
   No instrumentation has been done in either repo yet.

### Phase 1: ACL2 Submodule + Sorting Corpus Access — ~1 day

**Branch:** `mdd/acl2-submodule`

Add the ACL2 fork from the prototype as a git submodule so we have access to
`books/sorting/` and can run ACL2 for transcript generation.

**Steps:**
1. `git submodule add git@github.com:septract/acl2-lean.git acl2` pointing to
   the `acl2-lean` branch (which is a fork of the official ACL2 repo with
   community books included)
2. Add `acl2/` to `.gitignore`'s Lake exclusion so `lake build` doesn't scan it
3. Copy `acl2/books/sorting/{isort,perm,orderedp,how-many,bsort,msort,qsort,sorts-equivalent}.lisp`
   into `acl2_samples/sorting/` for easy access
4. Verify the 4-file minimal subset parses: `lake exe acl2lean translate`
   on `isort.lisp`, `perm.lisp`, `orderedp.lisp`, `sorts-equivalent.lisp`

**Deliverable:** The sorting corpus is accessible and parseable.

### Phase 2: Translator Hardening for Sorting Corpus — ~3-5 days

**Branch:** `mdd/translator-sorting`

Make the translator produce type-checking Lean output for the sorting corpus.
All theorems will be `sorry`'d — the goal is syntactic correctness only.

**Steps:**
1. **include-book chains** — Translate `(include-book "perm")` to
   `import ACL2Lean.Translated.Perm` with topological ordering of files
2. **Termination measures** — For recursive defuns, emit
   `termination_by acl2Count x` (or the appropriate arg) and
   `decreasing_by simp [acl2Count]; omega` using the Count.lean infrastructure
3. **Missing primitives** — The sorting corpus needs:
   - `lexorder` (already on branch)
   - `orderedp` (recursive, needs definition + translation)
   - `how-many` (recursive list count)
   - `perm` (permutation predicate — recursive)
   - `true-listp` (already on branch)
4. **Translation pipeline** — Add a `Translated/` directory for auto-generated files:
   ```
   ACL2Lean/Translated/
   ├── Perm.lean            ← from perm.lisp
   ├── Orderedp.lean        ← from orderedp.lisp
   ├── HowMany.lean         ← from how-many.lisp
   ├── Isort.lean           ← from isort.lisp
   ├── Bsort.lean           ← from bsort.lisp
   ├── Msort.lean           ← from msort.lisp
   ├── Qsort.lean           ← from qsort.lisp
   └── SortsEquivalent.lean ← from sorts-equivalent.lisp
   ```
5. **Verify** — `lake build` succeeds. Every translated defun type-checks.
   Every translated defthm compiles (with sorry).

**Key challenge:** Termination proofs for translated recursive functions.
ACL2's sorting functions recur on `(cdr x)` with `(endp x)` guards, which
maps to `decreasing_by` obligations provable via `acl2Count_cdr_lt_of_not_endp`.

**Deliverable:** The sorting corpus translates to Lean files that compile.

### Phase 3: Manual Sorting Proofs (Baseline) — ~5-7 days

**Branch:** `mdd/manual-sorting`

Hand-prove the sorting corpus theorems in Lean, using the semantic model.
This establishes what the automated replay should produce and stress-tests
the model for missing lemmas.

**Minimal subset (4 theorems):**
1. `orderedp-isort` — insertion sort produces an ordered list
2. `true-listp-isort` — insertion sort produces a true list
3. `how-many-isort` — insertion sort preserves element counts
4. `perm-isort` — insertion sort produces a permutation (commented out in
   ACL2 source but provable)

**Approach:**
- Define `orderedp`, `insert`, `isort` over SExpr using `lexorder`
- Prove key lemmas: `insert` preserves ordering, `insert` preserves how-many,
  `isort` is a permutation
- Use `acl2_induct` + `acl2_simp` + `omega` as the primary proof strategy
- Document which lemmas from Properties.lean / Count.lean / Lexorder.lean
  were needed (this feeds back to Phase 2)

**Deliverable:** `ACL2Lean/Manual/Sorting.lean` with fully-proven theorems.

### Phase 4: ACL2 Transcript Capture + Hint Bridge — ~5-8 days

**Branch:** `mdd/acl2-hint-bridge`

Run ACL2 on the sorting corpus, capture proof transcripts, and build the
hint bridge that parses them into structured replay data.

This is the most uncertain phase. ACL2 prints detailed English proof
commentary during certification. We need to extract actionable structure
from it.

**Steps:**
1. **Build ACL2** — From the submodule, `cd acl2 && make` (requires SBCL or CCL)
2. **Certify sorting books** — `cd acl2/books/sorting && ../../saved_acl2 < script.lsp`
3. **Capture raw transcripts** — Wrap ACL2 invocation to tee proof output to
   files. One transcript per `.lisp` file, containing all proof commentary.
4. **Build hint bridge** — New `scripts/acl2_hint_bridge.py` (or Lean tool)
   that parses raw transcripts into structured hint files. Extract:
   - Induction scheme (function name, variable, measure)
   - Case structure (subgoal IDs, hypotheses)
   - Applied rules (rewrite rules, lemma names, rule classes)
   - Theory context (enabled/disabled rules)
   The data model already exists in `Syntax.lean` (`ProofInstruction`,
   `GoalHint`, `TheoryExpr`) — the bridge populates these types.
5. **Lean-side loader** — New `ACL2Lean/HintBridge.lean` that reads hint
   files and produces `ReplayState` values consumable by the replay tactic.
6. **CLI integration** — Add `lake exe acl2lean hints <file> <theorem>`
   command that shows parsed hint data.

**Key challenge:** ACL2's proof commentary is English-language and not
machine-friendly. The commentary includes markers like "We now apply the
induction scheme suggested by (ISORT X)" and "by the :rewrite rule
PERM-APPEND" — these are parseable but fragile. The initial bridge should
focus on the sorting corpus patterns only. Broader coverage comes later.

**Alternative approach:** Instead of parsing English commentary, instrument
ACL2 (fork it, patch the waterfall) to emit structured traces directly.
More work upfront but more reliable. Decision: try commentary parsing first;
if it's too fragile, invest in instrumentation.

**Deliverable:** Structured hint files for every theorem in the sorting corpus,
plus Lean tooling to load and inspect them.

### Phase 5: Proof Replay Tactic — ~7-10 days

**Branch:** `mdd/acl2-replay`

Build the `acl2_replay` tactic that reads structured hints and drives Lean
proof automation.

**Architecture:**
```lean
/-- Reads a hint file and attempts to close the current goal using
    the ACL2 proof strategy as guidance. -/
elab "acl2_replay" file:str : tactic => do
  let hints ← loadHints file.getString
  for step in hints.steps do
    match step with
    | .induct scheme var =>
        -- Set up induction using the named scheme
        evalTactic (← `(tactic| acl2_induct $(mkIdent scheme) $(mkIdent var)))
    | .rewrite rule =>
        -- Apply the named lemma as a rewrite
        evalTactic (← `(tactic| simp [$(mkIdent rule)]))
    | .simplify rules =>
        -- Simplify with the given rule set
        evalTactic (← `(tactic| acl2_simp))
    | .use lemma =>
        -- Apply a specific lemma
        evalTactic (← `(tactic| exact $(mkIdent lemma)))
    | _ =>
        -- Fallback to general automation
        evalTactic (← `(tactic| first | acl2_grind | omega | decide))
```

**Steps:**
1. **Hint loader** — Parse structured hint files into `ReplayState`
   (using the types from Phase 4's `HintBridge.lean`)
2. **Step interpreter** — Map each replay action to Lean tactic(s):
   - `induct` → `acl2_induct`
   - `rewrite` → `simp [rule]` or `rw [rule]`
   - `simplify` → `acl2_simp` with the named rules
   - `use` → `exact`/`apply` the cited theorem
   - `theory-disable` → filter simp lemma set
   - `expand` → `unfold`
   - `do-not-induct` → skip induction, use rewriting only
3. **Fallback chain** — When a hint step fails:
   `acl2_grind` → `omega` → `simp_all` → `sorry`
4. **Reporting** — Track which steps succeeded, which fell back, which sorry'd
5. **Test on sorting corpus** — Replace the `sorry`s in Phase 2's translated
   files with `acl2_replay "hints/theorem_name.json"`

**Deliverable:** `acl2_replay` tactic that closes >50% of sorting corpus
theorems automatically.

### Phase 6: Iterate and Close Gaps — ongoing

**Branch:** `mdd/replay-iteration`

Iterate on the replay tactic to close remaining gaps:

1. **Missing lemmas** — The replay tactic will reveal which ACL2 lemmas are
   used as rewrite rules but haven't been translated/proven in Lean yet.
   Port these from the translated corpus.
2. **Automation gaps** — Where ACL2 hints don't map cleanly to Lean tactics,
   add specialised handlers (e.g., for ACL2's destructor elimination,
   generalisation, cross-fertilisation).
3. **Extend to full sorting corpus** — Beyond the 4-file subset, handle
   merge sort, quicksort, bubble sort, and sorts-equivalent.
4. **Coverage metrics** — Track: % of theorems closed, % of subgoals closed,
   average sorry count per theorem.

**Target:** >90% of subgoals closed automatically for the sorting corpus.

## Key Design Decisions

### 1. SExpr vs ACL2Object

The prototype used `ACL2Object` (flat: int/char/str/sym/cons). This repo uses
`SExpr` (nil/atom/cons with nested Atom/Number). We stay with `SExpr` — it's
what the existing codebase uses, and our feature branches already have proofs
adapted to it. The nested structure requires more case analysis in proofs but
has first-class `nil`.

### 2. Translated files: committed vs generated

Translated `.lean` files should be **committed** (not gitignored), because:
- They need to compile with `lake build`
- Reviewers can inspect the translation quality
- Downstream proofs import them

The translator is a dev tool; its output is the artefact.

### 3. Hint format: JSON vs S-expression

`Syntax.lean` already defines the structured types (`ProofInstruction`,
`GoalHint`, `TheoryExpr`) that hint data should populate. The hint bridge
(Phase 4) should produce JSON that maps to these types. The replay tactic
consumes the Lean-side types, not raw files. JSON is the intermediate
format for caching/inspection.

### 4. ACL2 as optional dependency

ACL2 is only needed for Phase 4 (transcript generation). All other phases work
without it. The submodule should be optional — `lake build` must succeed
without building ACL2.

## Risk Assessment

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| ACL2 transcripts lack structure for replay | Medium | High | Start with commentary parsing; fall back to ACL2 instrumentation; worst case use brute-force Lean automation |
| Hint bridge is hard to build | Medium | High | The data model exists in Syntax.lean; focus on sorting corpus patterns only; iterate |
| Termination proofs for translated functions | Medium | Medium | `acl2Count` infrastructure handles standard cases; manual `decreasing_by` for edge cases |
| Sorting corpus needs primitives not yet in model | Low | Medium | Identified upfront (lexorder, orderedp, perm, how-many); all are straightforward |
| Proof replay tactic too fragile | Medium | Medium | Graceful degradation: sorry'd subgoals, not failures. Manual proofs (Phase 3) provide baseline |
| ACL2 build/certification problems | Low | Low | The ACL2 fork is known-good; sorting corpus is well-tested upstream |
